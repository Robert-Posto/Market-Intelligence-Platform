Ce ia funcția dintr-un rând de surse

Contractul dintre cele două benzi. Nimic altceva nu trece: cauta_date nu știe că există un inventar, iar discovery-ul nu știe ce face un flow.

💡 De ce un tabel și nu un apel direct

Discovery-ul costă bani și are nevoie de aviz uman; extracția rulează zilnic. Dacă a doua l-ar chema pe primul, fiecare rulare zilnică ar reface descoperirea — 30 de bănci × 100 de pagini, degeaba. Tabelul e și punctul în care un om poate interveni: o sursă pusă pe status = pauza dispare din bucla de extracție fără să se atingă nimic din cod.

💡 Idee de implementare

Cu coordonatele exacte primite de la Google Places, construim o hartă interactivă cu toate agențiile/ATM-urile competitorilor, ca strat peste harta României — nu doar un tabel de adrese. Scopul nu e doar „câte agenții are banca X", ci identificarea zonelor neacoperite de competiție (județe/orașe cu densitate mică de agenții competitoare) — semnal direct pentru unde ar avea sens expansiunea rețelei proprii.

Opțiuni pentru anunțuri de angajare (secțiunea 2.5) — în ordinea priorității

URL-ul nu se caută separat. Pagina de carieră iese din banda de descoperire a figurii 2, ca orice altă sursă: propusă de crawl, aprobată de om, scrisă în surse și reverificată trimestrial. E deja în setul de link-uri pe care descoperirea îl aduce oricum — momentan e doar aruncată de filtrul de pagini editoriale. Costul marginal e aproape zero. Singura modificare de schemă: încă o valoare, cariera, în enumul surse.rol din DDL.

Diferența față de restul platformei începe după aceea: aici descoperirea dă poarta, nu ținta. Anunțurile sunt efemere, nu apar în sitemap, și se enumeră din spatele porții la fiecare rulare.

⚠️ Un anunț ratat devine un semnal fals

La produse, o pagină ratată e o lacună în acoperire. La joburi, un anunț ratat la enumerare arată identic cu un anunț dispărut, deci devine posting_closed — o informație de piață inventată. E același mecanism ca eșecul tăcut din figura 4, dar aici e regula, nu excepția: la fiecare rulare, tot ce nu s-a văzut arată ca ceva retras. De aceea o rulare care n-a reușit nu e un rezultat, ci o stare separată — „n-am putut verifica” trebuie să fie în date, nu în capul celui care citește raportul.

💡 De ce merită, și ce îl face mai valoros

O bancă angajează pentru ce construiește, nu pentru ce a construit deja: semnalul apare cu 3–9 luni înainte de lansarea produsului, iar el stă în aglomerare, nu în anunțul individual — cinci roluri de data engineer în trei săptămâni, la o bancă fără niciunul în ultimele șase luni. Cel mai valoros efect e însă corelarea cu app_composition din figura 5: un SDK nou detectat în fișierul de instalare, plus roluri deschise pe aceeași tehnologie, sunt două surse independente care spun același lucru. Separat, fiecare e o presupunere. Cost recurent: zero — nici furnizor, nici hardware.

Din cele 8 bănci din scope, Banca Transilvania și UniCredit răspund 403 (același WAF din analiza de acces, confirmat din două rețele diferite), iar Salt Bank publică doar pe LinkedIn. ⚠️ Append-only, nu actualizare

Fiecare rulare adaugă rânduri; nimic nu se suprascrie. Consecința practică: întrebarea „ce dobândă are banca X acum" nu e un SELECT simplu, ci „ultima valoare la sau înainte de data Y", pe grup. Și, fiindcă o pagină neschimbată nu produce rânduri noi — hashul oprește extracția — created_at spune „când am reextras", nu „când era valabil". Un index pe (id_sursa, id_produs, camp, created_at DESC) e obligatoriu, nu opțional.

💡 De ce produsele sunt un tabel, nu o coloană de text

Prima versiune amesteca produse reale cu măsuri: dae, dobanda-nominala și curs-valutar erau tratate ca produse, deci fiecare primea propriul apel de extracție pe aceeași pagină. Rezultatul, măsurat: comision_administrare_lunar apărea sub 8 etichete de produs diferite și dae sub 7. Un DAE nu e un produs — e o cifră care descrie un credit, deci e o valoare în camp, nu o linie în produse.

DDL, tabel cu tabel

PostgreSQL. Comentariile marcate -- NOU sunt diferențele față de db.sql din proiect; restul e schema existentă. Ordinea de creare e cea de mai jos: cheile externe cer tabelele părinte întâi.

1. banci

CREATE TABLE banci (
    id            BIGSERIAL    PRIMARY KEY,
    slug          TEXT         NOT NULL UNIQUE,   -- cheia de legatura cu scripturile
    nume          TEXT         NOT NULL UNIQUE,
    tier          SMALLINT     CHECK (tier BETWEEN 1 AND 3),
    segment_real  TEXT,
    rol           TEXT         NOT NULL DEFAULT 'competitor'   -- NOU
                  CHECK (rol IN ('competitor', 'referinta')),  -- NOU: Libra nu e competitor
    activ         BOOLEAN      NOT NULL DEFAULT TRUE
);

2. produse

CREATE TABLE produse (
    id       BIGSERIAL  PRIMARY KEY,
    nume     TEXT       NOT NULL UNIQUE,   -- slugul, nu denumirea de afisare
    segment  TEXT       CHECK (segment IN ('retail', 'imm-corporate')),  -- NOU
    grup     TEXT,                                                       -- NOU
    activ    BOOLEAN    NOT NULL DEFAULT TRUE
);

3. surse

CREATE TABLE surse (
    id                    BIGSERIAL    PRIMARY KEY,
    id_banca              BIGINT       NOT NULL
                          REFERENCES banci (id) ON DELETE CASCADE,

    tip_sursa             TEXT         NOT NULL
                          CHECK (tip_sursa IN ('url', 'aplicatie', 'reclama')),
    sursa                 TEXT         NOT NULL,
    rol                   TEXT         CHECK (rol IN ('produs', 'hub',
                                                      'conditii', 'context')),

    -- au sens doar pentru tip_sursa = 'url'
    format                TEXT         CHECK (format IN ('html', 'pdf', 'xml')),
    metoda                TEXT         CHECK (metoda IN ('http', 'playwright',
                                                         'manual')),
    robots_ok             BOOLEAN,

    produse               BIGINT[]     NOT NULL DEFAULT '{}',
    metoda_extractie      TEXT,
    metoda_verificata_la  TIMESTAMPTZ,   -- null cat timp `metoda` e o estimare

    frecventa             TEXT         CHECK (frecventa IN ('zilnic', 'saptamanal',
                              'lunar', 'trimestrial', 'la_descoperire', 'manual')),
    status                TEXT         NOT NULL DEFAULT 'activ'
                          CHECK (status IN ('activ', 'pauza', 'eroare',
                                            'blocat', 'retras')),
    ultima_rulare         TIMESTAMPTZ,
    legal_review_ref      TEXT,
    created_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT ck_surse_web_only CHECK (
        tip_sursa = 'url' OR (format IS NULL AND robots_ok IS NULL)
    )
);

-- Fara indexul unic, aceeasi adresa intra de doua ori: descoperirea produce
-- propuneri si se rerulează, deci o va propune din nou.
CREATE UNIQUE INDEX ux_surse_url     ON surse (sursa) WHERE tip_sursa = 'url';
CREATE UNIQUE INDEX ux_surse_non_url ON surse (id_banca, tip_sursa, sursa)
                                     WHERE tip_sursa <> 'url';
CREATE INDEX ix_surse_banca   ON surse (id_banca);
CREATE INDEX ix_surse_planif  ON surse (frecventa, ultima_rulare)
                              WHERE status = 'activ';   -- ce ruleaza la noapte
CREATE INDEX ix_surse_produse ON surse USING GIN (produse);

4. hashes

CREATE TABLE hashes (
    id          BIGSERIAL    PRIMARY KEY,
    id_sursa    BIGINT       NOT NULL
                REFERENCES surse (id) ON DELETE CASCADE,
    format      TEXT         CHECK (format IN ('html', 'pdf', 'xml')),
    hash        TEXT         NOT NULL,   -- pe textul sanitizat, fara date si ore
    hash_bytes  CHAR(64),                -- NOU: pe octetii bruti, pentru Bronze
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()   -- NOU

    -- NOU: cheia veche era UNIQUE (id_sursa, format), care permite UN singur
    -- rand per sursa. Cu ea nu se poate tine istoric de amprente, desi de
    -- asta exista tabelul.
);

CREATE UNIQUE INDEX ux_hashes ON hashes (id_sursa, format, hash);
CREATE INDEX ix_hashes_sursa  ON hashes (id_sursa, created_at DESC);

5. observations

CREATE TABLE observations (
    id                 BIGSERIAL     PRIMARY KEY,
    id_sursa           BIGINT        NOT NULL
                       REFERENCES surse (id)   ON DELETE CASCADE,
    id_produs          BIGINT        NOT NULL
                       REFERENCES produse (id) ON DELETE RESTRICT,

    camp               TEXT          NOT NULL,   -- din vocabularul inchis al produsului
    cod_scenariu       TEXT,                     -- ABONAMENT_GOLD, PLATA_ONLINE_SUB_50000

    valoare_num        NUMERIC(18,6),
    valoare_text       TEXT,                     -- 'gratuit', 'negociabil'
    unitate            TEXT          NOT NULL    -- NOU: era nullable
                       CHECK (unitate IN ('procent', 'lei', 'eur', 'usd', 'zile',
                              'luni', 'ani', 'numar', 'puncte_procentuale',
                              'altele')),        -- NOU: enumul extractorului

    -- Valabilitatea DECLARATA de banca, nu momentul observatiei.
    valabil_de_la      DATE,   -- NOU
    valabil_pana       DATE,   -- NOU

    -- Dovada. Fara ea, o cifra inventata arata ca una masurata.
    citat              TEXT          NOT NULL,   -- NOU: era nullable
    confidence         NUMERIC(4,3)  CHECK (confidence BETWEEN 0 AND 1),
    id_hash            BIGINT        REFERENCES hashes (id),   -- NOU: inlocuieste content_hash
    sursa_continut     TEXT          NOT NULL DEFAULT 'descarcare_proprie'  -- NOU
                       CHECK (sursa_continut IN ('descarcare_proprie', 'web_fetch',
                                                 'llm_parser', 'manual')),  -- NOU
    bronze_sha256      CHAR(64),   -- NOU: null = fara bytes bruti, nereverificabil
    conflict_scenariu  TEXT,       -- NOU: acelasi camp de mai multe ori, fara scenarii distincte

    verificat_de_om    BOOLEAN       NOT NULL DEFAULT FALSE,   -- NOU
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT now(),   -- NOU: axa temporala

    CONSTRAINT ck_obs_valoare CHECK (
        valoare_num IS NOT NULL OR valoare_text IS NOT NULL
    ),
    CONSTRAINT ck_obs_valabilitate CHECK (
        valabil_pana IS NULL OR valabil_de_la IS NULL
        OR valabil_pana >= valabil_de_la
    ),
    -- Coerenta pe care codul o impune deja: o valoare adusa prin web_fetch nu
    -- are bytes bruti, deci nu poate avea amprenta de Bronze.
    CONSTRAINT ck_obs_bronze CHECK (
        bronze_sha256 IS NULL OR sursa_continut = 'descarcare_proprie'
    )
);

-- Tabelul e append-only si va fi cel mai mare. Fara indexul asta, intrebarea
-- "ce valoare e in vigoare acum" scaneaza tot.
CREATE INDEX ix_obs_curent ON observations
    (id_sursa, id_produs, camp, created_at DESC);
CREATE INDEX ix_obs_produs ON observations (id_produs, camp, created_at DESC);
CREATE INDEX ix_obs_review ON observations (created_at DESC)
    WHERE verificat_de_om = FALSE;   -- coada de verificare umana

6. observations_curente

-- Valoarea in vigoare, per (sursa, produs, camp, scenariu). Append-only
-- inseamna ca "acum" nu e un SELECT simplu: o pagina neschimbata nu produce
-- rand nou, fiindca hashul opreste extractia, deci se cere ultima valoare
-- cunoscuta, nu una de azi.
CREATE VIEW observations_curente AS
SELECT DISTINCT ON (id_sursa, id_produs, camp, COALESCE(cod_scenariu, ''))
       *
FROM   observations
ORDER  BY id_sursa, id_produs, camp, COALESCE(cod_scenariu, ''),
          created_at DESC;
⚠️ Trei constrângeri care fac munca de verificare

citat TEXT NOT NULL — dacă poate fi null, plasa care prinde valorile inventate are o gaură. unitate cu enum — valoare_num = 1 a însemnat, în date reale, și „1 an” și „1 procent”. Iar ck_obs_bronze împiedică o combinație imposibilă: o valoare adusă prin web_fetch nu are bytes bruți, deci nu poate purta amprentă de Bronze. Codul o respectă deja; constrângerea o face imposibil de încălcat.
